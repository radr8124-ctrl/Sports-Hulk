# Sports Zenith — iPhone Safari first-party persistent login

Date: October 10, 2026 Eastern. User observed: "It also resets every time. I have to sign in." Existing Sports Zenith site `https://sportszenith.com`, not a new application.

## Reproduced and verified root causes
- `commercial_web/src/AuthShell.jsx` previously gated every initial `insforge.auth.getCurrentUser()` session restore on a plain localStorage `sports-zenith-auth-session` boolean flag. If Safari purged that hint, the app immediately treated a potentially valid refresh cookie as signed out without asking the identity provider. It then deleted the hint again for every provider error, conflating temporary failure with explicit sign-out.
- Original InsForge SDK has **in-memory** access-token storage by design. Real browser sessions rely on a **Secure, HttpOnly refresh cookie**. The original frontend pointed authentication at a separate `*.insforge.app` provider host; this makes that cookie third-party for `sportszenith.com`, where iOS Safari ITP can block or partition it. InsForge's original anonymous refresh response set `insforge_refresh_token` under `/api/auth` with `SameSite=None; Secure; HttpOnly`; refresh then returned 401 with no cookie. Neither the localStorage hint nor an unpersisted in-memory access token was genuine login persistence.

## Shipped fix
- **First-party authentication only in the production web app**: `commercial_web/src/insforge.js` now uses the exact browser origin (`https://sportszenith.com`) for the current passwordless InsForge SDK authentication calls. Non-HTTP native shells and Vite development preserve the existing provider fallback. Existing account/Survivor private API responses still require a server-validated Bearer JWT; a first-party cookie does NOT grant access to private entry records by itself.
- New tightly allowlisted **`commercial_web/first_party_auth_proxy.js`** and new server route before other APIs: precisely the six InsForge self-service `/api/auth/...` methods needed for anonymous config, code send, code verify/login, refresh, logout and signed-in session verification. It pins the upstream HTTPS provider from the server config. It doesn't proxy public database/admin methods, user-supplied URLs, arbitrary headers, other cookies, unrelated API operations or credentials. It rejects cross-origin POST/Fetch-Site CSRF and oversized/malformed bodies. It sets no-store and refuses non-JSON/redirect/upstream-failure responses. Only the original `insforge_refresh_token` cookie may be relayed, scoped `/api/auth`, with `HttpOnly; Secure; SameSite=Lax`, no upstream Domain, and original expiration/max-age retained. No JWT/refresh secret is printed or stored in localStorage. The provider's anonymous key is read on the server and used only for the pinned account service.
- **Important HTTP correctness fix:** SDK's POST `/api/auth/refresh` and POST `/api/auth/logout` have no request body or content-type, which is correct; the proxy must allow those two bodyless requests. The first HTTPS browser test caught this, and an independent Node regression asserts both work without JSON content-type. Code send and actual OTP session creation still require JSON.
- Reworked `AuthProvider` to **always attempt actual session recovery on initial page load**, not consult or write any localStorage auth hint. Concurrent refreshes are deduplicated to avoid rotating the same refresh token twice; sign-out increments a session generation so stale earlier requests cannot reinstall a just-logged-out user. Transient network/5xx errors no longer clear a previously verified in-memory user, while actual 401/403 and explicit sign-out are treated as not authenticated. Mobile Safari `visibilitychange` and persisted `pageshow` revalidate on resumption. A valid returned OTP login immediately fills verified account state, and original Bearer token is only held in the SDK's memory.
- No new username/password database or manual claim is introduced. Existing `ANNIE G 01` remains operator-linked to the verified account, with original five historical wins and used teams, and no Week 5 pick saved. The login change does not create, resubmit or backdate a pool pick.

## Boundaries / required owner action
- Full authenticated iPhone Safari acceptance still requires a real user to sign in once **AFTER deployment**, because old provider-origin cookies cannot reliably become new first-party cookies without another verified OTP login. We do not possess or reuse the user's email code. The new session should then survive repeated page reloads, returning to Safari and opening another regular Safari tab until the provider session expires, user signs out, browser cookies are cleared or Private Browsing closes. Session longevity follows the provider's cookie expiry and browser privacy settings, not indefinite permanent credentials.
- A user in a ChatGPT in-app browser vs native Safari, a different Safari profile, or private browsing may have a separate cookie jar. Consistent use of regular Safari on `https://sportszenith.com` is important. No authenticated real iOS session, iCloud sync, or actual email deliverability was impersonated or asserted.
- **Texans incident remains unresolved:** original private `ANNIE G 01` Week 5 still recorded no current picks as of the prechange readback; external Knockout Pool submission is separate and not proven. The login repair neither certifies a Texans pick nor edits the original Week 5 record after its deadline.
